# Demo Script: AI 小说创作工作台

这份脚本用于 B 站讲解视频、实习项目演示和 Wiki 展示。目标不是逐项背功能，而是让观众理解：这个项目把“小说创作”做成了一个可导入、可规划、可写作、可审核、可分支试错的工程系统。

## 演示口径

一句话介绍：

> 这是一个面向长篇小说作者的本地 AI 创作工作台，可以把已有小说导入成资料底座，再通过多 Agent 大纲、续写、审核和 Git 分支来管理不同剧情路线。

建议视频结构：

1. 先展示完整闭环，不先讲实现细节。
2. 再解释 Dify、Flask、Markdown 文件和 Git 为什么这样分工。
3. 最后展示剧情分支实验室，作为项目最有记忆点的部分。

## Part 1: 导入初始化

### Step 1. 打开本地工作台

用户动作：

- 启动本地 Dify、后端和前端。
- 打开 `http://127.0.0.1:5173`。

展示重点：

- 前端是一个写作工作台，而不是普通聊天页面。
- 左侧是项目资料，中央是当前文件或审阅区，右侧是 Agent 对话。
- 顶栏有 `书籍 / 导入` 入口。

风险备注：

- 如果 storage 是空的，首屏可能没有现成书籍，这是正常演示起点。

### Step 2. 导入番茄小说章节

用户动作：

- 点击 `书籍 / 导入`。
- 填入 Tomato-Novel-Downloader 的 `bulk_files` 目录。
- 点击预览。

系统行为：

- 后端扫描 `0000_书籍信息.txt` 和章节 txt。
- 将每章转换为 Markdown。
- 保留原文缩进、段落空行和阅读布局。
- 输出章节数量、总字数、目标文件名和质量门槛。

展示重点：

- 质量门槛会拦截空章、短章、重复章节、断号、碎行和下载器残留。
- 这一步证明系统不是“瞎导入”，而是有确定性清洗和风险检查。

### Step 3. 确认写入章节资料库

用户动作：

- 确认导入。

系统行为：

- 写入 `storage/<book_id>/chapters/*.md`。
- 写入 `import_report.json`。
- 在该书独立 Git 仓库中提交导入结果。
- 前端自动切到导入后的第一章。

展示重点：

- 每本书是一个独立本地仓库。
- 原文成为可被 Agent 读取、归档和引用的长期资料，而不是一次性上下文。

### Step 4. 初始化创作资产

用户动作：

- 依次调用读书存档、世界模型、文风学习和大纲 Agent。

系统行为：

- 读书存档 Agent 读取章节，沉淀资料摘要。
- 世界模型 Agent 从原文中萃取题材机制、人物关系、规则边界和状态事实。
- 文风 Agent 生成“叙事结构指纹、作者可读审查、续写硬约束”。
- 大纲 Agent 根据当前素材建立可继续创作的大纲底座。

展示重点：

- 系统不是只生成 `style_guide.md` 这种抽象文档，而是把原文萃取成 Agent 后续可执行的约束。
- `status_card.md` 的意义是记录最新章节后的事实状态，不让续写只靠模型记忆。

## Part 2: 创作循环

### Step 5. 头脑风暴

用户动作：

- 向灵感/大纲 Agent 提出创作问题，例如：

```text
基于当前第七世前期的主线，给我三个不同的推进方向。
```

系统行为：

- Agent 读取当前世界观、summary、状态卡和已有大纲。
- 输出多个候选主张。

展示重点：

- 头脑风暴不是闲聊，它会向后续主线大纲、篇章大纲和逐章节大纲传递。

### Step 6. 多级大纲萃取

用户动作：

- 选择一个头脑风暴方向。
- 要求 Agent 逐层萃取：
  - brainstorm
  - master outline
  - arc outline
  - chapter outline

系统行为：

- 每一层大纲都可以作为下一层输入。
- 作者可以在任意层打断、修正或回流。

展示重点：

- 这不是一次性生成 100 章，而是一个可审阅的规划流水线。
- 大纲层级越往下，越接近实际续写边界。

### Step 7. 续写三章

用户动作：

- 在逐章节大纲完成后，请续写 Agent 生成三章草稿。

系统行为：

- 续写 Agent 读取章节大纲、summary、status card、world model、style constraints、error archive。
- 以 `chapter_draft.md` 作为写入目标。
- 每章按“写一章 -> 字数/约束检查 -> 局部扩写或修改 -> 复验 -> 下一章”的方式推进。

展示重点：

- 续写不是全量替换，而应该以局部修改和约束校验为主。
- 字数、剧情边界和文风硬约束都要进入同一条生产链。

### Step 8. 审核与三选一

用户动作：

- 进入审阅工作台。
- 触发审核 Agent。

系统行为：

- 审核 Agent 检查：
  - 是否越过逐章节大纲边界。
  - 是否违反世界观和状态卡。
  - 是否违背文风硬约束。
  - 是否踩中错误档案中的禁令。
- 审核发现的可复用问题写入 `error_archive.md`。

作者选择：

- 亲自修改。
- 归档保留。
- 打回续写 Agent 局部重写。

展示重点：

- 人类不是被 Agent 替代，而是最终裁决者。
- Agent 的错误会沉淀为下一轮约束，形成自进化闭环。

## Part 3: 剧情分支实验室

这一段是项目的核心记忆点，建议放在视频后半段。

### Step 9. 从同一头脑风暴派生两个剧情分支

用户动作：

- 在同一个主线节点提出两个互斥主张：

```text
分支 A：主角提前暴露底牌，进入高压对抗。
分支 B：主角继续隐藏底牌，进入潜伏经营。
```

系统行为：

- 作者基于当前 Git 状态创建两个剧情分支。
- 每个分支都可以独立继续大纲、续写和审核。

展示重点：

- 分支不是复制文件夹，而是版本控制意义上的平行路线。
- 两条路线共享基础设定，但拥有独立草稿和演化历史。

### Step 10. 分支 A 和分支 B 独立续写

用户动作：

- 在分支 A 上生成一组三章。
- 切换到分支 B，再生成另一组三章。

系统行为：

- 两个分支的 `chapter_draft.md`、状态变化和错误档案可以不同。
- Git 视图能看到不同分支的提交和差异。

展示重点：

- 作者可以真实试写剧情，而不是只在脑子里想“如果这样会怎样”。
- 失败路线不会污染主线。

### Step 11. 对比、保留、合并或废弃

用户动作：

- 打开 Git/diff 视图比较两个路线。
- 选择一条路线继续，另一条保留或废弃。

系统行为：

- 好路线可以合并回主线。
- 坏路线可以回滚或保留为备选。

展示重点：

- 这就是 Git-native 小说创作的价值：剧情试错被工程化。

## 演示收束

最后用三句话收束：

1. 这个项目把长篇小说创作拆成资料、规则、规划、写作、审核和版本分支。
2. Dify 负责 Agent 编排，Flask 负责确定性工具和持久化，Git 负责创作路线试错。
3. 项目展示的不只是“会调 API”，而是把 AI 工作流、产品交互和工程治理组织成一个可演示的创作系统。

## Demo 风险与备选路线

- 如果番茄搜索暂未完成，就先从本地 `bulk_files` 导入开始演示。
- 如果完整百万字导入耗时过长，就使用小型样本证明流程，再说明同一机制可扩展。
- 如果 Dify 某个 Agent 不稳定，就展示前端审阅、Git 分支和后端 API 的确定性部分。
- 如果续写质量不理想，不要掩盖，而是借此展示审核、错误档案和局部重写闭环。
